# zbolt_toolchanger — тулченджер Z-Bolt как расширение Klipper

Расширение для двухголовых принтеров Z-Bolt с парковками и общим слайдером
(S300 / S310 / S400 / S600 HT Dual). Заменяет собой всё, что раньше было
размазано по `tools.cfg`, `homing.cfg`, `parking.cfg` и файлу переменных.

**Что забирает на себя:**

- датчики парковок (и, в будущем, датчик слайдера) с опросом в реальном времени;
- состояние тулченджера и матрицу аварийных ситуаций;
- парковку, захват, сцепку, вытирание сопла, буст тока драйверов;
- хоминг с восстановлением состояния;
- офсеты инструментов и калибровку Z-офсета второй головы.

**Файлы:**

| Файл | Назначение |
|------|------------|
| `klippy/extras/zbolt_toolchanger.py` | Модуль |
| `klippy/extras/zbolt_toolchanger_tool.py` | Обёртка секций инструментов |
| `docs/zbolt/zbolt_toolchanger.md` | Эта документация |

Рабочие примеры конфигурации — `klipper-config/zbolt_toolchanger.cfg`
профилей S300/S310/S400/S600 HT Dual в репозитории `Config_printer`.

---

## Зачем это сделано

В макросах состояние датчика читалось так:

```jinja
{% set Parking0State = printer['gcode_button t0_parking'].state %}
```

Jinja разворачивает шаблон **в момент постановки команды в очередь**, а хост
уходит вперёд машины на всю глубину очереди движений (`buffer_time_high`,
по умолчанию 2 секунды). Поэтому макрос читал датчик до того, как слайдер
физически доезжала до парковки. Компенсировали это слепой задержкой
`G4 P2000` в `T0`/`T1` — она примерно равна глубине буфера, но гонку иногда
проигрывала, и голова била в парковку.

Расширение опрашивает датчики только после `toolhead.wait_moves()`: хост
синхронизируется с реальным положением, и никакая задержка не нужна.
Дополнительно каждый фронт датчика приходит колбэком в реактор — за
миллисекунды и независимо от очереди g-кода, так что неожиданное срабатывание
обрывает последовательность немедленно.

---

## Установка

Модули входят в состав форка Z-Bolt (`klippy/extras/`), поэтому отдельно
ставить ничего не нужно — они приезжают вместе с обновлением прошивки:

```bash
cd ~/klipper && git pull
sudo systemctl restart klipper
# в консоли Klipper / Fluidd:
FIRMWARE_RESTART
```

На принтерах Klipper обновляется через `update_manager` в Moonraker.

Нужны оба файла: в Klipper имя секции = имя модуля.

| `sensor_settle_time` | `0.05` | Окно стабильности датчика, с. Замена `G4 P2000` |
| `sensor_timeout` | `3.0` | Сколько ждать стабильного состояния до аварии F7 |
| `verify_retries` | `1` | Повторов парковки/захвата при неподтверждении |
| `travel_speed` | `300` | Быстрое перемещение, **мм/с** (бывш. `speed_fast` 18000 / 60) |
| `dock_speed` | `60` | Медленный заход в парковку, мм/с (бывш. `speed_slow` 3600 / 60) |
| `force_speed_factor` | `0` | Принудительный `M220 S…` перед park/get; `0` — не трогать |
| `z_lift_before_home` | `5` | Подъём Z перед хомингом XY, **относительный** |

| `z_lift_speed` | `15` | Скорость Z-перемещений, мм/с |
| `home_axes_order` | `y, x` | Порядок хоминга осей |
| `home_z_position` | центр стола | Точка, где хомится Z |
| `after_home_position` | — | Куда отъехать после хоминга |
| `slider_sensor_pin` | — | Датчик наличия головы на слайдере (опционально); сработал = слайдер занят |
| `apply_offset_gcode` | `_SET_GCODE_OFFSET_INTERNAL X={x} Y={y} Z={z}` | Как применять офсеты |

| `service_mode_variable` | `service_mode` | Переменная флага сервисного режима |
| `before_change_gcode` | — | Выполняется перед каждой сменой инструмента |
| `after_change_gcode` | — | Выполняется после смены; **в сервисном режиме пропускается** |
| `calibrate_temp` | `160` | Температура сопел при калибровке офсета |
| `calibrate_stabilize_time` | `60` | Термостабилизация перед пробами, с |
| `calibrate_samples` | `3` | Число проб на инструмент |
| `on_fault_<код>` | см. матрицу | Реакция на класс аварии |

### `[zbolt_toolchanger_tool tN]`

| Параметр | Описание |
|----------|----------|
| `tool_number` | Номер: `0` → команда `T0` |
| `extruder` | Имя экструдера (`extruder`, `extruder1`) |
| `dock_sensor_pin` | Пин датчика парковки (бывш. `[gcode_button tN_parking]`); **сработал = голова в этой парковке**, полярность задаётся `!` в имени пина |

| `park_xy` | Координаты парковки (бывш. `tNx_park` / `tNy_park`) |
| `unpark_xy` | Точка выхода; по умолчанию = `park_xy` |
| `safe_xy` | Безопасная точка у парковки (бывш. `tNx_safe` / `tNy_safe`) |
| `stage_xy` | Промежуточная точка перед заходом (S300/S310) |
| `exit_xy` | Точка отъезда после захвата |
| `approach_offset` | Смещение по X, с которого начинается медленный заход |
| `retreat_speed` | `slow` или `fast` — скорость отхода после захвата |
| `wipe_moves` | Список `dx, dy` относительно `safe_xy` — вытирание об сопливчик |
| `coupling` | `solenoid` (S300/S310) или `latch` (S400/S600) |
| `solenoid_pin` | Имя `[output_pin]` электромагнита |
| `release_delay` | Пауза после снятия электромагнита, с (бывш. `delay`) |
| `release_jerk` | Рывок по Y для расцепления защёлки (бывш. `tNy_jerk`) |
| `release_jerk_speed` | Скорость рывка, мм/с |
| `seat_offset_xy` | Точка «дожима» головы (бывш. `_PUSH_EXTRUDER`) |
| `seat_jerk`, `seat_return_speed` | Параметры дожима |
| `current_boost` | Множитель тока X/Y на медленных участках; `0` — не менять |
| `current_boost_phase` | `park`, `get` или `both` |
| `offset_x_variable`, `offset_y_variable`, `offset_z_variable` | Имена переменных офсетов в `save_variables` |
| `park_gcode`, `get_gcode` | Полная замена траектории своим g-кодом (необязательно) |

Офсеты намеренно остаются в файле переменных: их правят при настройке
принтера, и расширение перечитывает их на каждой смене инструмента, без
рестарта. Вся парковочная геометрия, наоборот, живёт здесь.

### Траектория парковки и захвата

Порядок фиксирован, необязательные шаги пропускаются:

```
ПАРКОВКА                              ЗАХВАТ
  stage_xy                              сцепка armed (solenoid ON)
  safe_xy                               unpark_x, safe_y     быстро
  wipe_moves (от safe_xy)               park_xy              медленно
  safe_x, unpark_y                      защёлкивание (рывок)
  park_x + approach_offset              safe_x, unpark_y     retreat_speed
  park_xy               медленно        exit_xy              быстро
  расцепление
  unpark_x, safe_y      медленно
```

Если этого не хватает — задайте `park_gcode` / `get_gcode`; в шаблон
передаются `{park_x}`, `{park_y}`, `{unpark_x}`, `{unpark_y}`, `{safe_x}`,
`{safe_y}`, `{tool_number}`, `{fast}` и `{slow}` (последние два — в мм/мин,
готовые для `F`).

## Команды

| Команда | Что делает |
|---------|-----------|
| `T0`, `T1` | Выбор инструмента. Регистрируются модулем, макросов быть не должно |
| `TOOLCHANGER_SELECT TOOL=n [FORCE=1]` | То же явно; `FORCE=1` — повторить смену |
| `TOOLCHANGER_PARK [TOOL=n]` | Поставить инструмент в парковку |
| `TOOLCHANGER_PICKUP TOOL=n` | Забрать инструмент |
| `TOOLCHANGER_HOME` | Хоминг с восстановлением. Только из `[homing_override]` |
| `TOOLCHANGER_STATUS` | Показать состояние |
| `TOOLCHANGER_QUERY_SENSORS` | Мгновенный опрос датчиков |
| `TOOLCHANGER_SET_STATE TOOL=n\|NONE` | Задать состояние вручную при разборе аварии |
| `TOOLCHANGER_RELEASE` / `TOOLCHANGER_COUPLE` | Расцепить / сцепить |
| `TOOLCHANGER_CALIBRATE_OFFSET [TOOL=1] [TEMP=] [SAMPLES=] [STABILIZE=]` | Калибровка Z-офсета второй головы |
| `TOOLCHANGER_SAVE_ADJUST` | Сохранить подстройку Z с учётом офсета активной головы; вызывается из обёртки `SET_GCODE_OFFSET` |
| `TOOLCHANGER_SERVICE_MODE [ENABLE=1\|0]` | Сервисный режим настройки; без параметра показывает текущий |
| `TOOLCHANGER_GOTO TOOL=n POINT=park\|unpark\|safe\|stage\|exit [SPEED=]` | Подъехать к точке парковки |
| `TOOLCHANGER_SET_DOCK TOOL=n POINT=… [X= Y=]` | Записать координату точки (затем `SAVE_CONFIG`) |

`[homing_override]` сводится к одной строке:

```cfg
[homing_override]
gcode:
  TOOLCHANGER_HOME
set_position_z: 0
```

`TOOLCHANGER_HOME` вызывает вложенные `G28 X/Y/Z`, которые Klipper внутри
override направляет на настоящий хоминг. Вне override команду вызывать
нельзя — получится рекурсия.

## Три Z-параметра, которые легко перепутать

| Что | Где живёт | Кто меняет | Смысл |
|-----|-----------|-----------|-------|
| `z_offset` в `[probe]` | `bed.cfg`, секция `[probe]` | системный, не трогаем | Смещение датчика относительно сопла |
| `z_adjust` | файл переменных | оператор через `SET_GCODE_OFFSET` при печати | Подстройка первого слоя, **общая для обеих голов**: переносится между T0 и T1 |
| `t1_z_offset` | файл переменных | `TOOLCHANGER_CALIBRATE_OFFSET` | Разница высот между головами: хотенды не встают одинаково |

Итоговый офсет: на **T0** применяется `t0offset + z_adjust`, на **T1** —
`t1_z_offset + z_adjust`. То есть подстройка первого слоя сохраняется при
смене головы, а межголовая разница добавляется только для второй.

Переменная раньше называлась `offset_z`, а на части машин — `z_offset`, что
путалось с `z_offset` у `[probe]`. При обновлении такой машины переименуйте
ключ в файле переменных, иначе подстройка обнулится:

```
z_offset = -0.13   ->   z_adjust = -0.13
```

## Калибровка Z-офсета второй головы

`TOOLCHANGER_CALIBRATE_OFFSET` меряет **разницу высот сопел**, и меряет её так,
чтобы никакой посторонний офсет в результат не попал:

1. Один `G28` на обе пробы. Хоминг между измерениями сбросил бы общий ноль,
   ради которого всё и делается.
2. Прогрев обеих голов до `TEMP` и термостабилизация — холодное и горячее
   сопло стоят на разной высоте.
3. Проба опорной головой, затем калибруемой — **в одной физической точке**.
   Переезд выполняется g-кодом, а не в координатах кинематики: собственный
   X/Y-офсет головы применён как gcode-офсет, поэтому сопло каждой головы
   встаёт на одно и то же место стола.
4. Результат — разность двух измерений.

Разность отменяет всё общее для обеих проб: `z_offset` самой пробы, снос
хоминга, форму стола под этой точкой и поправку `axis_twist_compensation`.
Не влияют и `z_adjust` с прежним значением `t1_z_offset` — пробы идут в
координатах кинематики, а gcode-офсет на срабатывание датчика не действует.

В консоль выводятся оба измерения, чтобы результат можно было проверить
глазами:

```text
[+] T0: z=-1.000, T1: z=-0.850 -> офсет T1 = 0.150 мм
```

Если разность выглядит неправдоподобно — смотрите на сами измерения, а не
на итог: разъехавшиеся `z` опорной головы между запусками означают проблему
с хомингом или пробой, а не с офсетом.

## Сервисный режим

Нужен при сборке и настройке принтера, когда парковки ещё не выставлены и
головы снимают руками. Включается `TOOLCHANGER_SERVICE_MODE ENABLE=1`,
состояние хранится в файле переменных и переживает `FIRMWARE_RESTART`.

Что меняется:

- **`after_change_gcode` не выполняется.** На машинах, где компенсация
  перекоса включается этим хуком, она остаётся выключенной: `SET_SKEW`
  сдвигает координаты парковок, и настраивать их под включённой
  компенсацией бессмысленно
- **Аварии только предупреждают.** Реакции `pause`, `error` и `shutdown`
  понижаются до `warn`, чтобы сборщик мог снимать и ставить головы руками
- **Хоминг не забирает инструмент.** Оси XY хомятся, Z — только если голова
  уже на слайдере; если слайдер пуста, Z пропускается с сообщением

### Настройка координат парковки

```text
TOOLCHANGER_SERVICE_MODE ENABLE=1
G28                                   ; XY захомятся, голову никто не возьмёт
TOOLCHANGER_GOTO TOOL=0 POINT=safe    ; подъехать к безопасной точке
TOOLCHANGER_GOTO TOOL=0 POINT=park    ; медленно, dock_speed
; подвигать слайдер руками / джогом, поймать правильное место
TOOLCHANGER_SET_DOCK TOOL=0 POINT=park     ; записать текущую позицию
SAVE_CONFIG                                ; сохранить в zbolt_toolchanger.cfg
...
TOOLCHANGER_SERVICE_MODE ENABLE=0
```

`TOOLCHANGER_SET_DOCK` без `X`/`Y` берёт текущую позицию слайдера; можно
задать числа явно. Значение попадает в автосохраняемый блок конфига по
`SAVE_CONFIG`, файл руками править не нужно.

## Состояния и матрица аварий

Валидные состояния покоя:

| | T0 | T1 | Слайдер |
|---|---|---|---|
| **R1** | парковка | парковка | пуста |
| **R2** | слайдер | парковка | занята |
| **R3** | парковка | слайдер | занята |

Всё остальное — авария. Реакция каждого класса настраивается:
`ignore` (не реагировать), `warn` (сообщение), `pause` (ошибка + `PAUSE`,
если идёт печать), `error` (ошибка команды), `shutdown` (аварийный останов).

| Код | Когда возникает | Нужен датчик слайдера | По умолчанию | Что делать |
|-----|-----------------|------|--------------|------------|
| `both_undocked` | Обе головы вне парковок | нет | `pause` | Снять головы, поставить обе в парковки вручную, `FIRMWARE_RESTART` |
| `head_lost` | Голова не в парковке и не на слайдере | **да** | `pause` | Голова упала или отцепилась. Осмотреть механику, вернуть в парковку |
| `slider_unexpected` | Обе в парковках, но слайдер занята | **да** | `pause` | На слайдере посторонний предмет либо залип датчик |
| `park_failed` | После парковки датчик не подтвердил постановку | нет | `pause` | Проверить координаты парковки, сцепку, датчик. Автоповтор — `verify_retries` |
| `get_failed` | После захвата датчик всё ещё «в парковке» | нет | `pause` | То же: голова не снялась с парковки |
| `unexpected_edge` | Датчик сработал вне смены инструмента | нет | `pause` | Голова отцепилась на ходу либо дребезг проводки |
| `sensor_unstable` | Состояние не стабилизировалось за `sensor_timeout` | нет | `error` | Дребезг, обрыв, плохой контакт |
| `startup` | При старте состояние не соответствует R1–R3 | нет | `error` | Хоминг заблокирован; привести головы в порядок или `TOOLCHANGER_SET_STATE` |
| `change_while_unhomed` | Смена инструмента без хоминга | нет | `ignore` | Выполняется автоматический `G28` |
| `wrong_tool_active` | Активный экструдер не совпал с датчиками | нет | `warn` | Расширение поправит само |

Пример ужесточения реакции:

```cfg
on_fault_both_undocked: shutdown
on_fault_head_lost: shutdown
```

### Разбор аварии

1. `TOOLCHANGER_QUERY_SENSORS` — что реально видят датчики.
2. Привести головы в одно из состояний R1–R3 руками.
3. `TOOLCHANGER_STATUS` — убедиться, что состояние распозналось.
4. Если датчик врёт, а ехать надо: `TOOLCHANGER_SET_STATE TOOL=0` (или `NONE`).
5. `G28`.

## Полярность датчиков

Задаётся только именем пина, как у любого концевика Klipper: `^` —
подтяжка, `!` — инверсия. Отдельных опций вида «какое состояние считать
нажатым» нет.

Смысл сработавшего датчика:

| Датчик | Сработал |
|--------|----------|
| `dock_sensor_pin` | Голова **в этой парковке** |
| `slider_sensor_pin` | Слайдер **занят** головой |

На машинах Z-Bolt концевик парковки размыкается, когда голова в парковке,
поэтому пин пишется с инверсией:

```cfg
dock_sensor_pin: ^!PA1
```

`TOOLCHANGER_QUERY_SENSORS` печатает и электрическое состояние, и смысл:

```text
датчик парковки T0: не сработал — голова на слайдере
датчик парковки T1: сработал — голова в парковке
```

## Как читается состояние датчика

MCU присылает состояние кнопки **только при изменении** относительно нуля,
с которого начинает. Поэтому датчик, разомкнутый в момент загрузки, не
присылает вообще ничего: голова, стоящая в своей парковке, «молчит».

Расширение поэтому считает неотрапортованный датчик разомкнутым
(`RELEASED`) — ровно так же ведёт себя штатный `gcode_button`. Ждать доклада
нельзя: принтер завис бы на старте на той голове, которая в парковке.

Обратная сторона: оборванный провод датчика неотличим от «голова в
парковке». Проверять — командой `TOOLCHANGER_QUERY_SENSORS` с нажатием
датчика рукой.

## Поведение при старте

Через секунду после `klippy:ready` расширение опрашивает датчики, определяет
состояние **по железу** (а не по сохранённому значению), активирует
соответствующий экструдер без единого движения и печатает в консоль:

```
[+] Тулченджер: активная голова T0 (T0 — слайдер, T1 — парковка). Активный экструдер: extruder
```

Если состояние не распознано — печатается ошибка и хоминг блокируется.

## Что удалено из конфигов

Макросы: `_PARK_EXTRUDER`, `_PARK_EXTRUDER0/1`, `_GET_EXTRUDER`,
`_GET_EXTRUDER0/1`, `_PUSH_EXTRUDER0/1`, `_jerk_extruder`, `_jerk_extruder1`,
`_z_jerk`, `_SOL_ON`, `_SOL_OFF`, `CHECK_PARK0`, `CHECK_PARK1`,
`_START_CHECK0`, `PARKING_STATE`, `HOMING`, `_CHECK_PARK_HOME`, `T0`, `T1`,
`Zoffset`, `_GT1`; секции `[gcode_button t0_parking]` и `[gcode_button
t1_parking]`; файл `parking.cfg` целиком.

Переменные: `t0x_park`, `t0y_park`, `t0x_unpark`, `t0y_unpark`, `t0x_safe`,
`t0y_safe`, `t0y_jerk` и их `t1`-аналоги, `speed_fast`, `speed_slow`,
`delay`, `start_check`, `t0parking_state`, `t1parking_state`, `z_offset`.

Остаются в файле переменных: `t0offset`, `t1_x_offset`, `t1_y_offset`,
`t1_z_offset`, `offset_z`.

Для совместимости с кнопками KlipperScreen в `zbolt_toolchanger.cfg` оставлены тонкие
макросы-алиасы `Zoffset` → `TOOLCHANGER_CALIBRATE_OFFSET` и `PARKING_STATE`
→ `TOOLCHANGER_STATUS`.

## Типичные проблемы

1. **`Unknown config object 'zbolt_toolchanger'`** — модули не лежат в
   `~/klipper/klippy/extras/` или не сделан `FIRMWARE_RESTART`.
2. **`Command T0 already registered`** — где-то остался `[gcode_macro T0]`.
   Команду регистрирует расширение, макрос надо удалить.
3. **Головы едут не туда** — сверьте `park_xy` / `safe_xy` с прежними
   значениями из `toolchanger-settings.cfg`; в новом конфиге `safe_xy`
   задаётся числом, а не вычисляется как `park + 55`.
4. **Датчики всегда «в парковке» или всегда «на слайдере»** — перепутана
   полярность пина. На машинах Z-Bolt концевик размыкается при голове в
   парковке, поэтому нужен `!`: `dock_sensor_pin: ^!PA1`.
5. **Офсеты уезжают на каждой смене** — `apply_offset_gcode` должен вызывать
   `_SET_GCODE_OFFSET_INTERNAL`, а не `SET_GCODE_OFFSET`: последний
   переопределён в `bed.cfg` и записывает дельту в `offset_z`.
6. **`Must home axis first` при парковке** — расширение двигает слайдер
   напрямую; оси должны быть захомлены, либо вызов идёт из `homing_override`.
